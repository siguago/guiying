## 1. 这份计划要解决什么

本轮评估把问题分成两类：

- **A 类：实现没有兑现已有规范。** PRD 与 design-direction 已经写明的要求（目的地导航、可整理/为安全保留分区、批量接受建议、术语清洗、KPI 卡片墙 rework）在 `src/App.tsx` 中缺失或反向实现。这类问题不需要新决策，只需要补齐。
- **B 类：规范本身没有覆盖的缺口。** 逐组循环的交互模型在 700 组规模下不可用；隔离部分完成缺少三态语义；keeper 决策没有持久化落点。这类问题需要先补规范，再补实现。

两类问题的共同后果是：用户可以理解归影**为什么安全**，但无法在可接受的时间内**完成一次整理**。

本计划不扩展产品范围。永久删除、时间修复、D2/D3 与跨卷整理仍按 `ROADMAP.md` 第 12 节延期。

## 2. 问题登记

严重度定义：**S1** 阻断真实规模下的任务完成；**S2** 违反本仓库已生效的规范；**S3** 影响信任与理解，不阻断任务。

## 3. 整改方案

四个批次按「解锁任务完成能力 → 兑现已有规范 → 降低信任成本」排序。R1 与 R2 可并行，R3 依赖 R1 的 DTO 扩展。

### R1：把逐组循环改为一次扫描一份计划

**目标：** 用户完成一次 709 组整理所需的交互次数，从约 4,200 次降到 10 次以内。

**产品模型变更：**

扫描完成后不再要求用户逐组进入。结果页直接呈现：

1. 全部合格组的系统建议 keeper 与理由已就绪；
2. 一行计划摘要：「N 组可整理 · 将保留 N 个文件 · 将移入隔离区 N 个副本 · 逻辑 N GiB；M 组为安全保留」；
3. 主操作「接受全部建议并预览」，次操作「逐组复核」；
4. 用户可对任意组推翻建议、更换 keeper 或整组暂不处理，摘要实时更新；
5. 预览页列出整份计划（按组折叠），主操作文案带对象与数量：「将 2,184 个副本移入隔离区」；
6. 一次授权、一次执行、一份可整体恢复的操作记录。

**为什么这不放大安全风险：** `operation_batches` 与 `operation_items` 的一对多结构、`is_dry_run`、`requires_confirmation`、`sealed_at_ms` 与 item 级可重入状态机在 `0001_init.sql` 中已按批量设计。批量发生在**计划编译层**，执行仍是逐 item 的状态机与逐 item 的执行前复核。当前的单组实现是对该模型的退化，不是它的安全下限。

**改动点：**

| 层 | 改动 |
| --- | --- |
| IPC | 新增 `compile_quarantine_plan(resultReadToken, decisions[])`，接受多组 `{groupBuildId, keeperOrdinal}`；`select_quarantine_plan_root` 改为对整个 batch 授权一次，返回覆盖组数与预期项数 |
| `src-tauri/src/quarantine_service.rs` | 计划令牌绑定 batch 而非单组；执行遍历 items，逐项复核 descriptor、路径、挂载会话与逐字节内容；任一项失败按 item 记录并继续，卷级异常仍立即熔断 |
| `src/lib/backend.ts` | `QuarantinePlanSelection` 扩展为 batch 摘要；`executeQuarantinePlan` 返回逐项结果计数 |
| `src/App.tsx` | `keeperSelections` 升为跨组草稿；新增「接受全部建议」与计划摘要条；`plan` 阶段渲染整份计划 |

**退出条件：**

- 709 组合成语料下，接受全部建议到执行完成的用户交互不超过 10 次，系统目录选择器最多出现 1 次；
- 单组复核与推翻建议路径与批量路径产生同一份计划；
- 批量计划中任一不合格组不能通过任何前端路径进入 sealed batch；
- 每个 item 仍在执行前独立复核，`SAFETY.md` 的 P0 故障注入全部通过。

### R2：兑现已有规范

四项独立改动，互不依赖。

**R2-a 侧栏改为目的地导航。** 删除 `workflow` 常量与 `WorkflowRail`（`src/App.tsx:108`、`:220`），替换为 PRD 第 6 节的四个目的地。发布构建中隔离区在 M4 前不出现（ROADMAP M1 已有此约定）；活动与设置按当前实现能力决定是否显示。整理流程内部的位置改用工作区内的面包屑或标题表达，不使用永久可见的锁定步骤。

*退出条件：* 界面中不存在指向未实现能力的锁定步骤；侧栏每一项都是可点击且可到达的目的地；ROADMAP M1 退出条件第二条重新成立。

**R2-b 资格分区。** `DuplicateGroup` DTO 增加 `eligibility: 'eligible' | 'review_required' | 'blocked'`、`blockReasonCode`（稳定机器码）与 `blockReasonCopy`（用户可读原因）。资格由核心层判定，前端不得推导或覆盖。结果页分为「可整理」与「为安全保留」两区，后者不显示 Keep/Move 控件，只显示原因与可行的下一步。

*退出条件：* PRD FR-03 验收成立——相同证据产生相同分类，界面能回答「为什么这组暂时不能移动？」；`review_required` 与 `blocked` 组无法进入计划编译器。

**R2-c 术语清洗。** 常规界面替换下表词汇；高级证据、诊断导出与开发构建不变。

| 位置 | 现文案 | 目标文案 |
| --- | --- | --- |
| `src/App.tsx:183` | 封存范围文本 | 已扫描的位置 |
| `src/App.tsx:587`、`:635` | 封存结果目录 / 封印结果 | 活动记录 / 已完成的扫描 |
| `src/App.tsx:589` | 逐字节组已封印 | 内容已完整比对 |
| `src/App.tsx:657` | 封存显示文本 | 扫描时的位置 |
| `src/App.tsx:866`、`:2865` | 逻辑重复上限 | 重复占用（移入隔离区暂不释放空间） |
| `src/App.tsx:859`（组行） | D1 · 逐字节确认 | 组行移除；仅在成员详情与「为什么判定为完全相同」保留 |
| 顶栏 | D1 安全整理 | 移除 |

*退出条件：* 对 `src/App.tsx` 中非高级证据区域执行 `grep -n "封印\|封存\|逻辑重复上限\|D1"` 返回空；PRD FR-09 前半条成立。

**R2-d KPI 数字墙改为计划摘要。** 删除四格 `Metric`（`src/App.tsx:2863`–`2866`）。规模数字并入标题区一行正文；「需要留意」并入 R2-b 的「为安全保留」区标题；「重复占用」并入 R1 的计划摘要条。

*退出条件：* 结果页不存在与当前决策无关的数字格；design-direction 第 12 节该行的 rework 结论关闭。

### R3：状态语义与决策持久化

**R3-a 隔离三态。** 后端 `execute_quarantine_plan` 返回 `status: 'quarantined' | 'partially_quarantined' | 'needs_reconciliation'` 与逐项计数 `{moved, skipped, needsReconciliation}`，与 `operation_batches.state` 已有取值对齐。前端删除 `movedCount !== currentMoveCount` 的抛错（`src/App.tsx:2608`），改为渲染三态完成页：已移动 / 已跳过（含每项原因）/ 需对账（含下一步）。恢复侧同样处理 `partially_restored`（`src/App.tsx:2640`）。

*退出条件：* 注入「移动第 k 项后失败」，界面显示已移动 k 项且提供隔离区入口，不显示「错误」也不退回预览；content-map「部分完成不写成成功」与其反向情况同时成立。

**R3-b 决策持久化。** keeper 与「整组暂不处理」写入 `operation_batches`（`is_dry_run=1`、`state='planned'`）与 `operation_items(keeper_media_file_id, duplicate_group_member_id)`。同一 scan_run 下重开应用可恢复草稿；scan_run 失效时草稿标记过期并说明原因，不静默清空。

*退出条件：* PRD 11.1 第一条成立；重启后草稿可恢复且可审计；草稿本身不构成任何写授权。

**R3-c 已处理状态。** 执行成功后按 operation 结果更新组行状态，新增「已整理」态，与「已选保留」「请选择保留项」区分。

*退出条件：* 用户从完成页返回列表，可一眼区分已整理、已决策未执行、未决策三类组。

### R4：起点与扫描页降噪

**R4-a 起点页。** 安全承诺从六处收敛到两处：主区一句副标题，侧栏底部一处常驻声明。删除「安全整理原则 SAFE / 01」卡片（`src/App.tsx:377`），其内容并入首次运行的一次性说明或「先看证据」详情。侧栏「当前范围」移除 birthtime/mtime/atime，改为「扫描只读取，不修改照片」。四个入口降为一主两次：主操作「选择照片文件夹」，次要「活动记录」「恢复隔离文件」；合成数据演示仅在开发构建显示。

## 6. 验收

1. **规模任务：** 在 709 组 / 2,184 副本的合成语料上，未接受过培训的测试者在 10 分钟内完成一次「接受建议 → 复核并推翻至少一组 → 预览 → 执行 → 恢复」，全程不打开高级证据、不导出报告；

5. **安全回归：** `SAFETY.md` 的 P0 故障注入矩阵、现有 Rust 与 UI 自动化门禁全部通过，无一项因批量化而放宽；

### R2-b：资格分区（已完成）

判定放在核心层，前端只渲染结论：

- 新增 `scan_service::classify_group_eligibility`，从 feature gate 中移出上限常量，成为唯一的资格判定入口。判定只用扫描已封存的证据：成员数、剔除硬链接后的独立文件数、逻辑大小。
- `select_quarantine_plan_root` 改为调用同一函数。此前 UI 与执行准入是两套条件，可能让界面提供引擎会拒绝的组；现在不可能漂移。
- `DuplicateGroupItem` 增加 `eligibility` / `blockReasonCode` / `blockReasonCopy`，withheld 组必定同时带机器码与用户可读原因。
- 前端 `adaptGroupEligibility` fail closed：未识别的结论、自相矛盾的组合（eligible 却带原因）、以及说不出原因的 withheld 组，一律按 blocked 处理。前端无法把任何组提升为可整理。
- 结果页分「可整理 / 为安全保留」两区；withheld 组没有 keeper 控件、没有预览入口——不是禁用态，而是根本不渲染；检查器回答「为什么这组暂时不能移动？」并说明照片未被改动。

判定的当前覆盖范围：单成员组、硬链接组、大小证据异常（blocked），超过 256 个成员或 64 GiB 的组（review_required）。逻辑资产、独有 xattr/ACL、time donor 等 PRD 5.1 的其余条件仍待核心层补齐，届时只需扩展这一个函数。

测试：4 条 Rust 单元测试锁定分类器（含「withheld 必须能解释自己」），1 条 UI 测试锁定 FR-03 验收。

顺带修正：`.results-scale` 起初被插进 `.workspace-header, .results-header` 的选择器组中间，使扫描页标题失去内边距；分区标题用 `<h3>` 触发 heading-order，面板标题相应升为 `<h2>`；withheld 胶囊沿用了动作蓝，在琥珀底上既误读为可操作又不达 AA，已改为完整的 warning 语义。
